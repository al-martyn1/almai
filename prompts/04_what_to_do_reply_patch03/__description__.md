Короткий ответ: **для анализа ИИ лучше всего — не один формат, а комбинация: HAR + «нормализованный DOM-дамп» + отдельно исходники скриптов**. Причём подавать это ИИ надо не целиком, а через предварительную фильтрацию и разбиение на части.

Ниже — почему и как.

---

## 1. Почему ни один формат сам по себе не идеален

**MHTML** — один файл, удобно хранить, но:
- это MIME-контейнер с base64, для модели это шум;
- исходников в читаемом виде нет (JS и CSS внутри — как есть, но перемешаны с бинарём);
- нет структуры «запрос → ответ → тайминги»;
- ИИ по нему будет вынужден парсить вручную и половину потеряет.

**HAR** — хорош по сети, но:
- огромный (десятки-сотни МБ с телами);
- в телах лежат минифицированные бандлы без структуры;
- там нет DOM и нет того, что скрипты сделали со страницей;
- тайминги и заголовки — это метаданные, ИИ по ним мало что скажет без контекста.

**DOM-дамп через `outerHTML`** — то, что реально видит пользователь после скриптов, но:
- нет связи «этот элемент отрисован из этого JS»;
- нет сети;
- есть «мусор» вроде огромных inline `<script>` и SVG-иконок.

**Исходники (после source maps)** — самое ценное для понимания логики, но:
- их много;
- без контекста «где это используется» модель теряется;
- обычно минифицированы, если `.map` не отдали.

Вывод: для ИИ нужен **компактный, размеченный, избыточно-связанный** артефакт. Не «сырой архив», а «аналитический слепок».

---

## 2. Что реально «съедает» ИИ хорошо

Модели отлично работают с:
- **структурированным JSON** (HAR сам по себе — JSON, но слишком тяжёлый);
- **Markdown-описанием** сжатой картины;
- **кодом** — если он нормально отформатирован и не гигантский;
- **таблицами** ключевых фактов (метод, URL, статус, тип).

Модели плохо работают с:
- бинарём в base64;
- минифицированными однострочниками на мегабайт;
- файлами больше нескольких сотен тысяч токенов — теряют середину;
- «сырой» сетью без заголовков-аннотаций.

Значит, задача — **превратить сырьё в компактное представление**.

---

## 3. Практический рецепт: «AI-friendly bundle»

Соберите для ИИ один файл (или несколько), где лежат:

### 3.1. Сводка страницы (небольшой JSON)

```json
{
  "url": "https://ya.ru/",
  "title": "Яндекс — быстрый поиск",
  "finalHtmlLength": 51234,
  "domNodeCount": 1234,
  "scripts": 42,
  "stylesheets": 7,
  "requests": 138,
  "loadedAt": "2026-09-10T12:00:00Z"
}
```

### 3.2. Список запросов в компактной форме

Из HAR вырезать всё лишнее, оставить таблицу:

```
GET  https://ya.ru/                    200  html    51 KB  doc
GET  .../nova3/be91...js               200  script  1.2 MB  <script src>
GET  .../rythm-feed.js                 200  script  480 KB
GET  .../suggest-ya.cgi?...           200  json    3 KB    xhr
POST https://.../count/WJue...         204  text    0       img beacon
...
```

Это уже в разы меньше, чем HAR, и модель по нему сразу видит картину.

### 3.3. Нормализованный DOM

Из `outerHTML` убрать:
- inline-SVG (заменить на `<svg/>`),
- base64-картинки,
- `data-*` с мусором,
- длинные inline `<script>` (их — отдельно, см. ниже).

Оставить структуру: теги, id/class, ключевые атрибуты (`href`, `src`, `placeholder`, `role`, `aria-*`).

### 3.4. Каталог «точек взаимодействия»

Отдельным списком — все важные узлы:

```json
[
  {"selector":"textarea#text","role":"input","placeholder":"Найдётся всё","visible":true},
  {"selector":"button.search3__button","role":"submit","text":"Найти"},
  {"selector":"button.search3__voice","role":"button","aria":"Голосовой поиск"},
  {"selector":"a.headline__personal-enter","role":"link","text":"Войти"}
]
```

Модель сразу поймёт, что можно нажимать.

### 3.5. Исходники — кусками, а не целиком

Для каждого скрипта:
- имя, размер, source-map URL;
- если есть source map — распакованные исходники по файлам;
- если нет — **деобфусцированный** минифицированный код (`prettier` / `js-beautify`).

Каждый файл — отдельный артефакт. Модель загружает только те, что нужны по вопросу.

### 3.6. Динамика сети после загрузки

Отдельный блок «что ушло после `onLoad`»:

```
12:00:01.230  GET  /suggest/suggest-ya.cgi?...  200  json
12:00:01.240  GET  /portal/feed?...             200  json
12:00:01.500  POST /clck/click/...              204
```

Это то, что HAR обычно перегружает, а для ИИ — самое интересное (как страница жила после загрузки).

---

## 4. Что подавать ИИ в первую очередь

Если у вас ограничение по объёму контекста, порядок такой:

1. **Сводка + таблица запросов** (пара килобайт) — обязательно.
2. **Нормализованный DOM** (десятки-сотни КБ) — обязательно.
3. **Каталог точек взаимодействия** (килобайты) — обязательно.
4. **Исходники** — по требованию, по одному файлу за раз, с вопросами.
5. **HAR целиком** — почти никогда не нужен модели; нужен только вам как источник для пунктов 1–3.
6. **MHTML** — как архив для воспроизведения, не для ИИ.

---

## 5. Как это выглядит на практике

Один «AI bundle» — папка:

```
bundle/
  summary.json
  requests.tsv
  dom.html                 (нормализованный)
  interactive.json
  console.log
  scripts/
    be91c9...js
    be91c9...js.map
    rythm-feed.js
    ...
  network/
    post-load.tsv
  meta.json
```

И отдельно от bundle:

```
raw/
  page.har
  page.mhtml
```

Модели отдаёте `bundle/`, а `raw/` держите для себя — если что-то из bundle оказалось урезано, всегда можно вернуться и уточнить.

---

## 6. Почему именно такой порядок важен

ИИ отвечает на вопрос «как управлять страницей» лучше всего, когда видит **три вещи**:

1. **Что на странице есть** (DOM + селекторы + роли).
2. **Как оно появилось** (какие запросы, в каком порядке, что пришло).
3. **Как оно живёт** (что уходит после `onLoad`, какой API дёргается).

HAR даёт №2 и №3, но без №1. DOM даёт №1, но без №2–3. Только вместе они превращаются в понимание.

Минифицированный JS отвечает на вопрос «почему именно такой селектор» — но только если модель уже знает, что искать. Поэтому исходники — второй эшелон.

---

## 7. Чуть более продвинутый вариант: «diff-снимки»

Если вы снимаете одно и то же приложение несколько раз (например, после ввода текста в поиск), полезно снимать **не полный bundle, а diff**:

- что появилось в DOM;
- какие новые запросы ушли;
- какие обработчики сработали.

Это ещё компактнее и точнее отвечает на вопросы «что происходит, когда я делаю X».

Реализуется как два bundle + скрипт сравнения.

---

## 8. Итог

- **Для ИИ:** HAR в чистом виде — плохо, MHTML — плохо, DOM-дамп — лучше, но мало.
- **Лучший формат** — «нормализованная выжимка» из HAR + DOM + списка селекторов + разбитых по файлам исходников.
- **HAR и MHTML** держите как «сырьё для воспроизведения» и для досбора деталей.
- **Подавайте по частям**, а не «вот тебе 500 МБ, разбирайся».
- **Снимок + diff** при повторных сценариях — ещё полезнее.
