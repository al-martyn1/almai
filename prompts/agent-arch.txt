
## Как у меня организованы препромпты

У меня есть типы препромптов, я пока не особо знаю, зачем и почему я решил завести типы препромптов, 
но это какое-то упорядочивание в любом случае.

Пока типы препромптов просто задают структуру каталогов препромптов, и определяют, какие подкаталоги с препромптами будут сканироваться.

Типы препромптов задаются в файле опций (часть из них вычитывается на старте, часть - из проекта, или же задаётся пользователем, 
он же может задать конкретныую опцию впрямо в комндной строке). Файл опций имеет формат: одна строка - одна опция, допустимы пустые строки и коментарии.

Типы препромптов (категории) задаются в `preprompt-type.options`.

***conf/preprompt-type.options***
~~~
# role/roles
# не задаём, данный тип всегда существует

# skill — процедурное умение: способность решать класс задач.
--add-preprompt-type=skill

# instruction — инструкции: шаги, порядок действий, правила выполнения.
--add-preprompt-type=instruction

# knowledge — декларативные знания: факты, определения, предметная область.
--add-preprompt-type=knowledge

# template / format — шаблон ответа, структура документа, формат.
--add-preprompt-type=template

# Выходной формат документа?
#--add-preprompt-type=output

# tool / function — вызов API, кода, внешнего сервиса.
--add-preprompt-type=tool
--add-preprompt-type=function

# workflow / process — последовательность шагов или оркестрация нескольких скилов.
--add-preprompt-type=workflow

# policy / rule / constraint — правила, запреты, ограничения, safety, compliance.
--add-preprompt-type=policy

# heuristic / strategy — эвристика, стратегия действий в неопределённости.
--add-preprompt-type=strategy

# pattern / anti-pattern — типовое хорошее или плохое решение.
--add-preprompt-type=pattern
--add-preprompt-type=anti-pattern

# example / few-shot — примеры входа-выхода.
--add-preprompt-type=example

# checklist / validator / test — проверка качества, критерии, тесты.
--add-preprompt-type=checklist

# memory / context — память, профиль, предпочтения, история.
--add-preprompt-type=context
--add-preprompt-type=history

# goal / intent — цель, намерение, критерии успеха.
--add-preprompt-type=goal 

# resource / asset — файлы, данные, ссылки, скрипты, изображения.
--add-preprompt-type=asset

# feedback / metric — обратная связь, метрики, оценка результата.
--add-preprompt-type=feedback
--add-preprompt-type=metric
--add-preprompt-type=kpi
~~~


## Как лучше размечать

Как я понял, препромпты надо размечать в виде XML документа (может быть, и не так строго и формально, каким должен быть машинно-обрабатываемый XML, но примерно так же).

Далее, структуру создаваемого промпта мы делим на три части:
- Зона A — рамка (pre-context). Кто агент, что делает, какие правила.
- Зона B — контекст (context). Документы проекта, описания, манифест аттачей.
- Зона C — контракт (post-context). Формат ответа, чек-лист, напоминания.


Вместо зон intro/final в препромте, как я понял, в нем предлагается вводить использовать XML-тэги.
В твоих примерах я нашел такие тэги:
- <role>
- <constraints>
- <skills>
- <tools>
- <output_format>
- <checklist>

И ещё такие:
- <task>
- <docs>/<doc>
- <attachments>/<manifest>

Первая группа явно отвечает за то, какие части препромптов в какие разделы финального промпта будут вставлены.
Нужно:
- продумать, какие ещё тэги в препромпте могут быть, какой смысл они несут и в каой раздел финального промпта они должны быть вставлены.
- продумать возможность расширения, то есть, задавать их не в коде, а через опции командной строки (и, соответственно, через файл опций).

Например, задаём секции препромптов:
~~~
--prepromt-section=role
--prepromt-section=constraints
--prepromt-section=skills
--prepromt-section=tools
~~~

Тут не важно, единственное число или множественное, я умею преобразовывать одно в другое.

Далее, надо как-то задать порядок вставки этих секций в финальный промпт:
~~~
--pre-context=role,task,constraints,skills
--context=docs,attachments
--post-context=output_format,checklist
~~~

Тут надо ещё предусмотреть возможность очищать списки `pre-context`, `context` и `post-context`.
Допустим, элемент '-' - очищает весь соответствующий список, а элемент с префиксом '-' - '-skills'
удаляет только один конкретный элемент, если он был в списке.

Тут есть ещё проблема - секция <task> у нас как бы предопределённая, туда вставляется
содержимое собственно того промпта, который я ввожу в систему.

Может, позволить задавать имя секции также через командную строку?
Например:
~~~

# в примере выше сначала идёт внутреннее имя, и через двоеточее - используемое в опциях --pre-context, --context или --post-context

## Секция <docs>

Ты приводишь примеры секции <docs>:

~~~
<docs>
  <doc path="ARCHITECTURE.md">...</doc>
  <doc path="README.md">...</doc>
</docs>
~~~

~~~
<docs>
  <doc path="ARCHITECTURE.md" role="descriptive">
    ...полный текст ARCHITECTURE.md, включая вложенные code fences...
  </doc>
  <doc path="README.md" role="descriptive">
    ...полный текст README.md...
  </doc>
</docs>
~~~

Тут у меня вопросы такие. Можно считывать фиксированные файлы и помещать их в секцию <docs>
в фиксированном порядке, но хотелось бы иметь возможность это тоже настраивать при помощи опций
командной строки (или их указанием в файле опций).

Также атрибут 'role' у тэга <doc> надо уметь задавать.
Возможно, атрибут 'role' - это короткое имя для описания документа, а полное идёт в под-тэге <description>,
а само держимое документа идёт в под-тэге <content>.

~~~
<docs>
  <doc path="ARCHITECTURE.md" role="descriptive">
    <description>
    </description>
    <content>
    ...полный текст ARCHITECTURE.md, включая вложенные code fences...
    </content>
  </doc>

  <!-- ... тут ещё <doc> тэги -->

</docs>
~~~

Чтобы не переусложнять одну опцию, предложим несколько таких опций:
~~~
# задаём секцию в <docs>
--doc-section=arch
# задаём атрибут role
--doc-section-opt=arch:role:текст атрибута role
# задаём имя файла, если такой файл существует, то документ включается, иначе - просто пропускается
--doc-section-opt=arch:file:ARCHITECTURE.md
# задаём описание документа (тэг <description>)
--doc-section-opt=arch:description:Описание документа

~~~

В тэг <content> включаем собственно само содержимое документа.

## Отступы

Обычно XML форматируется с отступами в 2/4 пробела.
Когда внутри XML тэга вставляется текстовый документ, то есть варианты:
- вставить, как есть - в этом случае отступ вставленного документа будет выбиваться из общего формата
- добавить ко всем строкам вставленного документа отступ, как для вложенного тэга.

## Инструмент `dir`

В разделе <grammar> надо как-то указать, что маски могут содержать два метасимвола:
- '*' - любое число любых символов
- '?' - один любой символ

Эти правила примерно соответствуют формату масок файлов в системах DOS/Windows, они просты для использования
и не требуют постоянного экранирования, как всевозможные спец символы в регулярных выражениях.
А сами эти символы запрещены в именах файлов.

Ещё надо указать запрещённые символы. Тут надо собрать все запрещённые в именах файлов символы систем Windows и Linux.
