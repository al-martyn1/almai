Когда большая языковая модель (LLM) решает вызвать внешнюю функцию или API, она генерирует специальный текст, который затем перехватывает управляющая программа (парсер).
Поскольку единого мирового стандарта нет, разные семейства моделей выдают тег <tool_call> (или его аналоги) совершенно по-разному. Ответы бывают четырех основных видов:


1. Гибридный вид: JSON внутри XML-тегов (Тот самый Hermes JSON)

Это именно тот формат, из-за которого произошел конфликт в вашей фразе. Модель использует XML-теги, чтобы программе-парсеру было легко найти границы вызова, но внутри самих тегов пишет чистый JSON-объект с именем функции и её аргументами.
• Кто использует: Модели семейства Hermes (Nous Research), Qwen (в определенных режимах), MiniMax.
• Пример:
```xml
<tool_call>
  {"name": "get_weather", "arguments": {"city": "Moscow", "days": 3}}
</tool_call>
```


2. Чистый XML-вид (Теги внутри тегов)

В этом случае модель вообще не использует фигурные скобки и синтаксис JSON. Параметры функции передаются как вложенные XML-ноды (атрибуты или теги).
• Кто использует: Семейство моделей Qwen 3 / Qwen-Coder, кастомные промпты (вероятно, тот самый froggeric из вашей фразы) и некоторые конфигурации Anthropic Claude.
• Пример:
```xml
<tool_call>
  <function=get_weather>
    <parameter=city>Moscow</parameter>
    <parameter=days>3</parameter>
  </function>
</tool_call>
```


3. Чистый JSON-вид (Без тегов / Native API)

Модель возвращает «голый» JSON или массив объектов. В этом случае нет никаких <tool_call> в тексте, а сервер вывода (например, vLLM или Ollama) сразу передает этот массив в специальном поле ответа API (tool_calls).
• Кто использует: OpenAI (GPT-4o), современные модели от Mistral и Llama при работе через официальные API.
• Пример:
```json
[
  {
    "id": "call_123xyz",
    "type": "function",
    "function": {
      "name": "get_weather",
      "arguments": "{\"city\": \"Moscow\", \"days\": 3}"
    }
  }
]
```


4. Псевдо-код или Python-стиль

Некоторые современные модели обучают писать вызовы функций так, будто они пишут код на обычном языке программирования (например, Python).
• Кто использует: Llama 3.1 / 3.2 (в нативном режиме работы с Python-инструментами).
• Пример:
```python
get_weather(city="Moscow", days=3)
```
*(Или с использованием кастомных квадратных скобок: `[get_weather(city="Moscow")]`)*


## XML

С точки зрения строгого стандарта W3C XML, этот синтаксис не является валидным XML.

в настоящем XML у тега не может быть знака равенства (=) прямо в его имени. Значения могут присваиваться только атрибутам внутри открывающего тега (например, <function name="get_weather">).
То, что генерируют LLM в данном случае, в среде разработчиков называют «псевдо-XML», «ИИ-XML» или «XML-подобными тегами».

Такой «сломанный» синтаксис появился не из-за стандартов интернета, а из-за особенностей обучения моделей (Tokenization и Prompt Engineering):
1. Экономия токенов: Конструкция <function=get_weather> банально короче и тратит меньше токенов (а значит, работает быстрее и дешевле), чем валидная <function name="get_weather">.
2. Лень разработчиков парсеров: На стороне ИИ-агента этот текст никто не отправляет в строгие XML-парсеры (вроде lxml или xml.etree). Разработчики фреймворков часто пишут под них простые регулярные выражения (Regex), например: r"<function=(.*?)>". Раз регулярка это легко «съедает», авторы моделей не усложняют промпты обучением строгому XML.
Поэтому в контексте системных промптов и ИИ-агентов под словом «XML» почти всегда скрывается вот такой самописный «суррогат» разметки.
